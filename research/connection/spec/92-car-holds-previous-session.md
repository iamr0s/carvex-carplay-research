# 92 — 车机持有旧会话时对 0x5702 沉默

日期：2026-11-06。基线手机与宿主不变。本文是**运行观察**（`OBSERVED`），不是固件结论：
它记录的是「手机发出 0x5702 之后车机完全没有反应」这一现象在同一台车、同一晚、同一份
声明的两轮里出现与不出现的对照，以及它对我们判断「连接为什么卡住」的影响。

[91](91-wifisharing-start-feature-5702.md) 说明 0x5702 是 feature 22 的启动动作、
一个会话只发一次。本文补上另一半：**只发一次之后，如果车机安静，那安静本身是什么。**

## 1. 两轮对照

同一台 Android 车机（CarWith 宿主），同一晚，同一个 APK（`20069`），手机侧声明、代码、
车型都没有变。两轮相隔 6 秒：

| | 轮 A（`9303b8c4`） | 轮 B（`4bacf53d`） |
|---|---|---|
| 5702 实际发出 | `14:32:38` 前后 | `14:32:48.267296` `iAP frame TX 40/86/57/1/6 csm=5702` |
| 链路层重传 | — | `14:32:49.268097` 同 seq 86 重传一次 |
| 链路 ACK | 已到（`send()` 返回） | **始终没有** |
| 应用层结论 | `14:32:38.708951` `iAP TX 5702` | `14:32:50.279458` `CarHoldsPreviousSessionException`（3000ms 无 ACK） |
| 之后 | `14:32:38.713936` `stage WIFI`（**+5ms**） | 该会话终止 |
| 后续 | `14:32:41.7` `stage PAIR`、`14:32:43.1` `stage SETUP` | 见 §4 |

轮 A 里 5702 到进 WIFI 是 **5 毫秒**；轮 B 里 5702 出去之后一秒钟内连一个字节都没回来。
同一部手机、同一条代码路径，差别只在车机的状态。

## 2. 关键：两轮的声明逐字相同

```text
14:32:46.739681 [4bacf53d] INFO Identify accessorySends=[0x5000, 0x5002, 0x5003, 0x5700,
  0x5703, 0xAA06, 0xEA02] receiverCanReceive=[0x4E09, 0x4E0A, 0x4E0B, 0x4E0C, 0x4E0D,
  0x4E0E, 0x5001, 0x5701, 0x5702]
14:33:49.866843 [5fe47be3] INFO Identify accessorySends=[0x5000, 0x5002, 0x5003, 0x5700,
  0x5703, 0xAA06, 0xEA02] receiverCanReceive=[0x4E09, 0x4E0A, 0x4E0B, 0x4E0C, 0x4E0D,
  0x4E0E, 0x5001, 0x5701, 0x5702]
```

`5702` 出现在车的 `receiverCanReceive` 里、`5703` 出现在 `accessorySends` 里，两轮完全一致。
也就是说 [91](91-wifisharing-start-feature-5702.md) §2.3 那个前置门在两轮里都成立：
**门不是变量，状态才是变量。**

这条排除了一个很自然的错误结论——「车机没声明 5702，所以我们不该发」。它声明了。

## 3. 沉默发生在链路层，不是业务层

`iAP frame TX ... csm=5702` 是字节真的写出去的日志；`iAP TX 5702` 是 `send()` 尾部打的，
只有所有 tx slot 都被 ACK 之后才会出现（`IapLink.kt:1031`）。轮 B 只有前者的两行（
含一次同 seq 重传），没有后者；轮 A 有后者。

所以轮 B 不是「车机收到 5702 但拒绝执行」，而是**车机在 iAP 链路上对它完全没有应答**。
这也和 [91](91-wifisharing-start-feature-5702.md) 的静态结论不冲突：发送侧没有重发路径，
链路层有界重传用完之后，手机侧收到的就是「安静」。

## 4. 恢复：4 次尝试，第 4 次成功，车机没有重启

| 会话 | 开始 | 结果 |
|---|---|---|
| `4bacf53d` | `14:32:44.290` | 5702 无 ACK，`14:32:50.279` 判沉默 |
| `8389a47b` | `14:32:50.588` | `14:32:57.809` `EOFException Truncated 0/2` |
| `d9f7d28e` | `14:33:01.144` | 停在 `BLUETOOTH`，没有进 `DETECT` |
| `5fe47be3` | `14:33:44.268` | `14:33:50.469` 发 5702，`14:33:50.498983` `iAP TX 5702`，`+11ms` 进 `stage WIFI` |

从第一次被沉默（`14:32:44.5`）到被接受（`14:33:50.5`）约 **66 秒**。这一晚车机
**没有断电重启**，前 3 次尝试每次只发一帧 5702（应用层），没有叠加重发。

作为对照，同一台车在更早的一轮里，手机端每 5 秒重发、25 秒预算内最多 6 帧，车机随后
断电重启。两种节奏的差别与上面这 66 秒的等待方向一致：**安静期里少发，车机会自己放行；
持续压它，它会复位。** 后者只有一次观察，不能当定律。

## 5. 对手机侧实现的影响

`android/` 当前把单次握手的等待上限锁在 30 秒：

```text
Bootstrap.kt:112   ANNOUNCEMENT_WAIT_MS = 30_000
Bootstrap.kt:334   require(handoffWaitMs in 1..30_000L)
Bootstrap.kt:477   到期 break
Bootstrap.kt:498   throw HANDOFF_FAILED
```

也就是**任何一次尝试都不可能等待超过 30 秒**。而本文记录的这台车从被沉默到放行用了约
66 秒。两者放在一起的结论不是「把 30 改成 70」——那只是把一个没有固件对应物的常量换成
另一个（[91](91-wifisharing-start-feature-5702.md) §3.1、WS-OPEN-04）。能说的是：

- 在这类车机上，**单次尝试注定覆盖不了持有期**，恢复只能来自「不在持有窗口内重复发问」；
- 所以判断依据不该是「等了多久」，而是「车机在这个会话里有没有应答过任何东西」；
- 真要把恢复做对，需要的是一条有界的跨尝试状态（例如记录「刚被沉默过」并在下一次
  尝试前避让），而不是一个更大的常数。

我们自己在 20070 里选择的是后者的粗糙版本：把「刚被拒绝的时刻」持久化，45 秒内不再发
5702。**这个 45 秒是本地取值，不是本文的结论，也不建议上游照抄**——它只是把
「别在窗口内重问」这条观察落到一个具体数字上，等 WS-OPEN-04 或车机侧证据出现后应当被替换。

## 6. 不能从本文得出的

- **不能说车机有一个 66 秒（或 45 秒）的超时。** 这是一台车、一晚、4 次尝试的观察值。
  真正在释放旧会话的是车机哪条路径、释放条件是什么，属于 WS-OPEN-01，仍 `OPEN`。
- **不能说所有车机都会这样。** 反过来说，别的车机可能有别的表现形式（拒绝、1D03、
  直接断开），本文没有观察。
- **不能说重发一定会让车机重启。** 那是一次观察，样本 1，没有对照实验。
- **不能把 66 秒写成代码里的固定延迟。** 按 [`AGENT.md`](../../../AGENT.md) §4，
  「盲试固定延迟」是禁止项；这条观察的正确用法是判断「当前这个会话还有没有希望」，
  而不是决定「睡多久」。
